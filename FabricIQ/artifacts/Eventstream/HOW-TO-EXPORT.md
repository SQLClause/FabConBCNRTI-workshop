# How to export: FreezerTelemetryEventstream

## Why this folder doesn't already contain the item definition

Fabric's `fab export` command produces a `.platform` file plus an item-definition
payload whose exact binary/JSON shape is generated by the service and is not
publicly specified as something safe to hand-author. Fabricating one here
without a live tenant to validate it against would risk silently breaking the
provisioning script for every attendee — the opposite of this workshop's
"fool proof" goal. Instead, the presenter creates the real item once by hand
in a dev tenant, wires up its source and destination, then exports the
tenant-verified definition into this folder before the event.

## Steps (do this once, in a dev/test tenant, ahead of the event)

1. In your scratch/dev workspace, create `ColdChainEventhouse` and its
   `ColdChainKQLDB` database first (see `../Eventhouse/HOW-TO-EXPORT.md`) —
   the Eventstream's destination needs the KQL DB to already exist. (The
   Lakehouse is unrelated to this item and doesn't need to exist here — the
   provisioning script creates it directly with no dev-tenant hand-build
   step, see `../Lakehouse`'s entry in `setup/manifest.yaml`.)
2. Select **+ New item > Eventstream**, and name it exactly:
   ```
   FreezerTelemetryEventstream
   ```
3. **Add the source — a custom endpoint:**
   - In the Eventstream editor, select **Add source > Custom endpoint** (this
     may be labeled **Custom App** depending on your Fabric capability tier —
     both expose the same connection mechanism).
   - Give it a source name (e.g. `FreezerTelemetrySource`) and save.
   - **Do not** try to script this connection string retrieval — it is only
     obtainable from the portal *after* the item exists, which is exactly why
     `setup/provision_fabric_iq.py` deliberately stops at creating the
     Eventstream item and hands off the "copy the connection string" step to
     the attendee during `lab-10` (see `BUILD_PLAN.md`, provisioning step 9).
4. **Configure the destination — the KQL database:**
   - Select **Add destination > Eventhouse**.
   - **Workspace**: your scratch workspace. **Eventhouse**: `ColdChainEventhouse`.
   - **KQL Database**: `ColdChainKQLDB`.
   - **Destination table**: `FreezerTelemetryRaw` (create it via the KQL
     script in `../Eventhouse/ColdChainKQLDB.kql` first if it isn't already
     showing up in the picker).
   - **Data format**: JSON.
   - **Input data schema / mapping**: if prompted, map the incoming JSON
     fields 1:1 to the table's columns (`FreezerId`, `StoreId`, `Timestamp`,
     `TemperatureC`, `DoorOpen`) — this matches
     `FreezerTelemetryRawMapping` defined in the KQL script.
   - Select **Save**, then **Publish** the eventstream.
5. Confirm the topology in **Live view**: `FreezerTelemetrySource` (custom
   endpoint) → default stream → `ColdChainEventhouse.ColdChainKQLDB.FreezerTelemetryRaw`.
6. From your terminal, with the Fabric CLI installed and authenticated:

   ```bash
   fab export "<dev-workspace-name>.Workspace/FreezerTelemetryEventstream.Eventstream" -o artifacts/Eventstream/
   ```

   Run this from the repo root so `-o` resolves to this folder.

   > **Note:** `fab export` was confirmed live to fail with a generic
   > `"UnexpectedError"` against a bare, just-created Eventstream on this
   > CLI version — untested against a fully wired-up one like this. If it
   > fails for you too, hand-edit the checked-in `eventstream.json` instead
   > of trying to regenerate it from scratch (its structure is plain JSON
   > and already documented by step 7 below).
7. **Replace the hardcoded destination IDs with placeholders** before
   committing — this is required regardless of whether step 6 worked, and is
   the actual reason this file previously didn't work for any attendee but
   the presenter who built it. In the exported (or hand-edited)
   `eventstream.json`, under `destinations[0].properties`:
   - `workspaceId` → literal string `__WORKSPACE_ID__`
   - `itemId` → literal string `__KQLDATABASE_ID__` — **must be the KQL
     database's own item ID, not the Eventhouse container's**; confirmed
     live that passing the Eventhouse's ID instead fails with `"Unable to
     extract cluster URL from the Eventhouse KQL database item ID ..."`

   `setup/provision_fabric_iq.py`'s `create_eventstream_item()` substitutes
   real IDs into these placeholders at import time (`item.parent_kql_database`
   in `manifest.yaml` names which KQLDatabase item to resolve), the same
   pattern the Notebook uses for `__LAKEHOUSE_ID__`/`__WORKSPACE_ID__`.
8. Confirm the exported files landed under
   `artifacts/Eventstream/FreezerTelemetryEventstream.Eventstream/`.
9. Commit the exported folder to git.

## Important: the connection string is per-workspace, not exported

Exporting/importing the Eventstream item definition does **not** carry a
reusable connection string — each attendee's freshly-imported Eventstream
gets its own custom-endpoint credentials, generated by the service when the
item is created in *their* workspace. This is expected and is why:

- `setup/provision_fabric_iq.py` provisions the Eventstream item but cannot
  and does not attempt to configure `artifacts/generator/freezer_telemetry_generator.py`
  automatically.
- Each attendee must, during `lab-10`, open their own
  `FreezerTelemetryEventstream` → source node → **Details** pane → copy the
  **Event Hub-compatible connection string**, and paste it into the
  `# TODO` marker at the top of `freezer_telemetry_generator.py`.

## Validate before the event

Re-run `setup/provision_fabric_iq.py --dry-run` against a second, throwaway
workspace and confirm: the Eventstream imports with its source and
destination topology intact, a fresh connection string is retrievable from
its **Details** pane, and events pushed with that connection string via
`freezer_telemetry_generator.py` show up in `FreezerTelemetryRaw` within a
few seconds.
