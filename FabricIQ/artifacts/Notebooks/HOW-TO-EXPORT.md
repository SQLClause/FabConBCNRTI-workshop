# How to export: 00_LoadReferenceData

## Why this folder doesn't already contain the item definition

Fabric's `fab export` command produces a `.platform` file plus an item-definition
payload whose exact binary/JSON shape is generated by the service and is not
publicly specified as something safe to hand-author. Fabricating one here
without a live tenant to validate it against would risk silently breaking the
provisioning script for every attendee — the opposite of this workshop's
"fool proof" goal. Instead, the presenter creates the real notebook item once
by hand in a dev tenant, pastes in the real code, then exports the
tenant-verified definition into this folder before the event.

The notebook's actual code **is** written out for real in this folder, at
[`00_LoadReferenceData.py`](00_LoadReferenceData.py) — it's plain, runnable
PySpark, not a fake Fabric notebook binary format.

## Steps (do this once, in a dev/test tenant, ahead of the event)

1. In your scratch/dev workspace, make sure `ColdChainLakehouse` already
   exists and has the three CSVs uploaded to `Files/SampleData/` (see
   `../Lakehouse/HOW-TO-EXPORT.md`, step 3).
2. Select **+ New item > Notebook**, and name it exactly:
   ```
   00_LoadReferenceData
   ```
3. Attach the default Lakehouse: in the notebook's **Explorer** pane, select
   **Add data items > Add > Existing data source** (or the Lakehouse picker
   at the top of the notebook), and choose `ColdChainLakehouse`. This makes
   `Files/...` paths inside the notebook resolve to that Lakehouse.
4. Open [`00_LoadReferenceData.py`](00_LoadReferenceData.py) from this repo,
   copy its full contents, and paste it into the notebook's first cell (or
   split it across cells at the `# COMMAND ----------`-style comments if you
   prefer a more granular walkthrough for the lab).
5. Run all cells. Confirm in the Lakehouse **Tables** section that three new
   managed Delta tables now exist: `Customers`, `Stores`, `Freezers`.
6. From your terminal, with the Fabric CLI installed and authenticated:

   ```bash
   fab export "<dev-workspace-name>.Workspace/00_LoadReferenceData.Notebook" -o artifacts/Notebooks/
   ```

   Run this from the repo root so `-o` resolves to this folder.
7. Confirm the exported files landed under
   `artifacts/Notebooks/00_LoadReferenceData.Notebook/`.
8. Commit the exported folder to git.

## Whether the provisioning script needs to also *run* the notebook

Importing a notebook item does **not** automatically execute it. After
`setup/provision_fabric_iq.py` imports `00_LoadReferenceData`, the Lakehouse
tables will **not** exist yet until the notebook is run at least once.

- For the live workshop, running the notebook is folded into `lab-01`/`lab-02`
  as an explicit attendee step (open the notebook, **Run all**) — this is
  good pedagogy anyway, since seeing the reference data land as Delta tables
  is itself part of what Module 02 teaches about grounding signals.
- `setup/provision_fabric_iq.py` intentionally does **not** attempt to
  trigger a notebook run via `fab job run` as part of provisioning (see
  `setup/provision_fabric_iq.py`'s flow comments) — keeping the script's
  scope to "create the plumbing" and leaving "run the notebook" as a visible,
  teachable lab step rather than something that happens invisibly before
  attendees ever see the item.

## Validate before the event

Re-run `setup/provision_fabric_iq.py --dry-run` against a second, throwaway
workspace, then manually run the imported `00_LoadReferenceData` notebook and
confirm all three Delta tables land with the expected row counts (6 stores,
15 freezers, 20 customers).
